# Design — encrypted diabetes-risk MLP

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._

This document describes the model, how it is evaluated homomorphically, the
crypto parameters and their depth rationale, the threat model, and how the
model and the encrypted run score on the held-out test set. For build
and run see the [README](../README.md); for the Niobium record and replay flow
see [NIOBIUM_INTEGRATION.md](../NIOBIUM_INTEGRATION.md).

## 1. Problem

Given a patient's answers to 21 questions from the CDC's BRFSS health survey
(blood pressure, BMI, smoking, physical activity, general health and so on),
estimate whether the patient has **diabetes or prediabetes**. The positive class
is 15.3% of records, so the task is scored on the rare class: precision, recall
and F1 at a fixed threshold, plus ROC-AUC. Raw accuracy is not informative at
that base rate.

The privacy goal is batch scoring on an untrusted server. A data owner (a
clinic, insurer or researcher) holds many patient records, encrypts them, and
gets back one risk score per record, **without the server seeing any feature
or any score in the clear**.

## 2. Model

### Reference: XGBoost

The reference is a bounded-depth XGBoost classifier
(`model/xgb_diabetes_model.json`; its hyperparameters are in the
[README](../README.md#the-model)). On the 45,895-record test split it reaches
ROC-AUC 0.8194 and diabetes-class F1 0.4776 at threshold 0.64, the
F1-maximizing threshold rounded. The training record,
`model/diabetes_model_metrics.json`, gives its operating-point figures at the
unrounded 0.6425.

Its 500 trees of depth-5 comparisons are not arithmetic, so they do not map to
CKKS. The circuit instead evaluates a small MLP distilled from it.

### Surrogate: 21 → 16 → 1 MLP

```
input (21, standardized)
  → Linear(21 → 16) → sigmoid
  → Linear(16 → 1)                        → 1 logit
```

- The output is the **logit** of P(diabetes). The client applies the threshold
  after decryption: diabetes when `logit ≥ ln(0.64/0.36) ≈ 0.5754`, which is
  `proba ≥ 0.64`, the reference model's operating point.
- In the circuit each hidden unit's sigmoid is a **degree-27 Chebyshev series**
  fitted over that unit's own input interval (§3). This approximation, not FHE
  noise, is the main source of difference between the circuit and the exact
  surrogate.

**Distillation.** The MLP was trained on the same 80% train split the XGBoost
model was fit on (183,579 rows, stratified, seed 42), regressing the XGBoost
**logits** (soft targets) rather than the labels. scikit-learn `MLPRegressor`,
adam, batch 512, learning rate 1e-3, **L2 α = 0.1**, early stopping on a random
10% of the train split, `random_state=42`. The test split was not used for the fit.
Standardization uses the train split's feature means and standard deviations.
The strong L2 is what keeps the hidden pre-activations inside a compact range
the Chebyshev series can cover (§8).

**Artifacts.** `model/surrogate/mlp_surrogate.json` holds everything needed to
run the surrogate: `W1` (21 × 16), `b1` (16), `W2` (16), `b2`, the scaler `mu`/`sd`,
`feature_cols`, `threshold_logit`, and the circuit's per-unit Chebyshev
coefficients and domains (`cheb_coefs`, `dom_lo`, `dom_hi`, `cheb_degree`).
`model/surrogate/feature_bounds.csv` is the raw feature box (§3).
`data/inputs/model.txt` is the same model exported for the C++ stages. Its c0
Chebyshev coefficients are doubled to match OpenFHE's series convention (§8),
so do not read it as plaintext weights.

The surrogate in plaintext, with the exact sigmoid:

```python
import json, numpy as np
S = json.load(open("model/surrogate/mlp_surrogate.json"))
W1, b1 = np.array(S["W1"]), np.array(S["b1"])
W2, b2 = np.array(S["W2"]), S["b2"]
mu, sd = np.array(S["mu"]), np.array(S["sd"])

def predict_logit(X_raw):                 # X_raw: (n, 21) in feature_cols order
    z = (X_raw - mu) / sd
    h = 1 / (1 + np.exp(-(z @ W1 + b1)))
    return h @ W2 + b2

pred = (predict_logit(X) >= S["threshold_logit"]).astype(int)
```

[`harness/cleartext_impl.py`](../harness/cleartext_impl.py) is the same forward
pass with the Chebyshev series in place of the sigmoid, read from
`data/inputs/model.txt`. It is the reference every run is graded against.

## 3. Homomorphic evaluation

**Client, before encryption.** The client standardizes each record,
`z = (x − mu) / sd`, and checks it against the **feature box**: the BRFSS code
book's range for every feature (binary flags, small ordinals, BMI 12–98, day
counts 0–30), in standardized units from `data/inputs/client_meta.txt`. A
record outside the box is malformed data and is rejected before encryption; on
the test split none is. The client then packs **column-major**: ciphertext `j`
holds feature `j` for up to 32,768 records, one per slot. That is 21
ciphertexts per slot-batch.

**Server, per slot-batch** ([`src/diabetes_compute_sdk.cpp`](../src/diabetes_compute_sdk.cpp)):

1. **Hidden layer:** `pre_k = Σ_j W1[j,k] · ct_j + b1[k]` for each of the 16 units,
   ciphertext × plaintext scalar multiply-accumulate. 1 level.
2. **Activation:** `h_k = EvalChebyshevSeries(pre_k, c_k, lo_k, hi_k)`, degree 27
   over the unit's own interval. 6 levels, with ciphertext × ciphertext
   multiplications inside the series.
3. **Output layer:** `logit = Σ_k W2[k] · h_k + b2`. 1 level.

The server returns **one** logit ciphertext per slot-batch. Because every slot
holds a different record and each layer works feature by feature, the circuit
needs **no rotations**, so no rotation keys, and **no bootstrapping**. The
weights enter as plaintext scalars.

**Domains are provable.** Each unit's Chebyshev interval `[lo_k, hi_k]` is an
interval-arithmetic bound of `pre_k` over the whole feature box, not an
envelope observed on data. Every record that passes the box check is therefore
inside every unit's interval by construction. That matters under batched
packing: one out-of-range slot would corrupt the whole slot-batch's decode.

**Multiple slot-batches.** `⌈records / 32,768⌉` slot-batches run the identical
circuit with the same keys and context. The full test split is two
slot-batches.

## 4. Crypto parameters and depth budget

CKKS at ring dimension `N = 2^16` (32,768 slots), multiplicative depth 11,
45-bit scaling modulus, 60-bit first modulus, `FLEXIBLEAUTO` rescaling,
`HEStd_128_classic`; the [README](../README.md#security-and-parameters) lists
it in full alongside the `CCParams` from
[`src/common.hpp`](../src/common.hpp). CKKS fits: the circuit is real-valued,
and its decisions tolerate far more noise than CKKS adds (§7). BFV or BGV would
force a fixed-point emulation of the sigmoid for nothing.

**Depth accounting.** The circuit consumes 8 levels: 1 for the hidden layer, 6
for the degree-27 series, 1 for the output layer. Depth 11 adds one level for
`FLEXIBLEAUTO`'s extra rescale and two spare.

**Decode safety.** The largest value decoded is the logit, `|logit| ≤ ~17`
(about 4.1 bits). With two spare levels the output still has
`60 + 2 × 45 = 150` bits of modulus, well above the
`45 + 4.1 + 10 = 59.1` bits the scale, the value and a 10-bit noise margin need.

**Security.** `logQ ≈ 60 + 11 × 45 = 555` bits, and with the key-switching
modulus added the total is still well inside the Homomorphic Encryption
Standard bound for `N = 2^16` at 128-bit classical security. The ring dimension is set
explicitly; it is also the size the Niobium backend runs.

**Sizes.** An input ciphertext at full level is
`2 × 65,536 × 12 limbs × 8 bytes ≈ 12.6 MB`, so a slot-batch's 21 inputs are
about 264 MB, roughly 8 KB per record when the slots are full. The output is a
single ciphertext at a low level. The server also needs the context and the
relinearization key; on the Fog each slot-batch is its own job and carries
them.

## 5. Security

**Parties.** The **client** is the data owner: it generates every key, keeps
the secret key, encrypts its own records and decrypts its own scores. The
**server** is honest-but-curious: it follows the protocol and inspects
everything it receives. Passive network observers see the same ciphertexts.

**Message flow.**

| When | Client → server | Server → client |
|---|---|---|
| With every slot-batch | `context.bin`, `key_relin.bin` | — |
| Per slot-batch | 21 input ciphertexts, `manifest.txt` (record counts) | 1 logit ciphertext |

The secret key and the plaintext records stay on the client. The compute stage
refuses to run if `key_secret.bin` is in its home, and
[`harness/run_submission.py`](../harness/run_submission.py) checks that on
every run by planting the key and requiring the stage to stop.

**What each party learns.**

| Party | Learns | Never learns |
|---|---|---|
| Client | its own records and all their scores | — |
| Server | the model, ciphertext sizes, slot-batch count and record counts, timing | any feature, any score, any intermediate value |
| Network observer | the same as the server, without the model | the same |

Confidentiality rests on CKKS (IND-CPA under RLWE, 128-bit classical) and on
the secret key never leaving the client.

**Incidental leakage.** The record count per slot-batch is visible in
`manifest.txt`; pad slot-batches to 32,768 records if that matters. The circuit
is fixed, so compute time depends on the number of slot-batches only. The
feature-box check runs on the client before encryption, so the server never
sees a rejection, and the box is the public survey code book, which says
nothing about the model.

**Output.** The scores go only to the party that owns the records, so the
output discloses nothing new and needs no rate limiting or differential
privacy. The decryptor is the consumer, so there is no output-integrity
problem either. If scores were ever passed to a third party (an insurer, say),
both questions would need revisiting.

**Outsourced evaluation.** If the server offloads the circuit to a remote
accelerator, as the Fog run does, the accelerator receives what the server
would hold: the ciphertexts, the relinearization key, and the model, whose
weights and Chebyshev coefficients are plaintext constants in the recorded
trace. Patient data stays confidential; the model is disclosed to the
accelerator's operator. Treat a remote evaluator as part of the server. In this
repository the model is public anyway: `data/inputs/model.txt` holds it.

**Not addressed.**

- A **malicious server** could return wrong ciphertexts. That costs result
  quality, not privacy; there is no verifiable-computation layer.
- **Compromise of the client host**, side channels on it, or theft of
  `key_secret.bin`.
- **Model extraction** by the client, who can query freely. The model is not
  treated as sensitive here.
- **Post-quantum margin:** the parameters target `HEStd_128_classic`; use
  `HEStd_128_quantum` (a smaller `logQ` or larger ring) if the threat model
  needs it.

## 6. Data

The records are the CDC's *Diabetes Health Indicators* (BRFSS 2015): 229,474
de-identified survey responses after removing exact duplicates, 21 features
([`data_dictionary.md`](../data_dictionary.md)), and the label
`Diabetes_binary`. They ship as a fixed, stratified 80/20 split (seed 42). The
encrypted run uses the standardized test split in `data/inputs/`. Full
provenance, the licence and the regeneration commands are in
[`../data/README.md`](../data/README.md).

## 7. Decision and evaluation

The client decrypts one logit per record and flags diabetes risk when
`logit ≥ 0.5754`.

Every run recomputes the plaintext circuit with
[`harness/cleartext_impl.py`](../harness/cleartext_impl.py), checks it against
the committed twin logits in `data/inputs/twin_logits.csv`, and grades the
decrypted logits against it with
[`scripts/check_batches.py`](../scripts/check_batches.py). A slot-batch fails if
any record's logit differs by `1e-3` or more, or if any decision flips. The
same script reports the run's precision, recall and F1 against the labels.

The `1e-3` tolerance comes from the decision margins. In the plaintext circuit
the closest record sits 6.2e-5 from the threshold and the first percentile
0.021 away. Gaussian noise of σ = 5e-5 flipped no decision in five trials;
σ = 1e-3 flipped about 6 of 45,895.

**Where the differences come from**, on the 45,895-record test split:

| Version | AUC | Precision | Recall | F1 | Cost of this step |
|---|---|---|---|---|---|
| Reference (XGBoost) vs labels | 0.8194 | 0.3910 | 0.6136 | 0.4776 | — |
| Surrogate (exact sigmoid) vs labels | 0.8195 | 0.3932 | 0.6075 | 0.4774 | distillation: 97.09% decision agreement with XGBoost |
| Circuit in plaintext (twin) vs labels | 0.8195 | 0.3932 | 0.6074 | 0.4774 | Chebyshev + provable domains: 2 flips vs the surrogate, max logit error 7.6e-4 |
| Encrypted vs twin | — | 0.3932 | 0.6074 | 0.4774 | encryption: 0 flips, max logit error far inside the 1e-3 tolerance |

The encrypted run's exact error differs from run to run, because each run draws
fresh encryption noise, and fresh keys when started with `--fresh`. Its size is set by the parameters, so it
stays around 1e-7, four orders of magnitude inside the 1e-3 tolerance every run
is checked against. With no decision flipped, the encrypted row's metrics equal
the twin's.

Nearly all disagreement with XGBoost enters at distillation, and task quality
against the labels is unchanged end to end. Perfect agreement with the twin
shows the encrypted run reproduces the model; how well the model predicts
diabetes is the separate question the first rows answer.

## 8. Design history

The scripts in [`scripts/design/`](../scripts/design/) produced the surrogate,
its Chebyshev fits and the twin; their docstrings refer to the steps of the
original design process ("Stage 3" for the surrogate, "Stage 7" for the twin).
Decisions worth keeping:

- **Not encrypting the trees.** Tree comparisons are not CKKS arithmetic;
  evaluating them encrypted means quantizing the model to small integers,
  which costs accuracy. Distilling to an MLP keeps the circuit to CKKS
  arithmetic with no loss.
- **Retraining for range.** The first surrogate (α = 1e-4) matched XGBoost but
  its hidden pre-activations spanned [−22.8, +17.7] over the full corpus, too
  wide for a low-degree fit. A sweep over α ∈ {1e-4 … 1} and 8 or 16 hidden
  units (`alpha_sweep.py`) found α = 0.1 with 16 units narrowed the range to
  ±14.4 at no cost in fidelity.
- **Degree 27.** Measured with the actual fitted polynomials on the test split:

  | Degree | Levels | F1 | Agreement with exact surrogate | Max logit error |
  |---|---|---|---|---|
  | 7 | 5 | 0.4757 | 98.79% | 0.217 |
  | 13 | 5 | 0.4772 | 99.83% | 0.026 |
  | 27 | 6 | 0.4774 | 100.00% | 2.2e-4 |

  Degree 27 costs one level more than 13 and matches every decision.
- **Provable over empirical domains.** The observed envelope plus 5% margin
  (largest interval 15.3) is slightly tighter than the interval-arithmetic
  bound over the feature box (16.9), and costs nothing in decisions; the
  provable bound costs 2 flips in 45,895. The provable bound was chosen because
  it guarantees every valid record is in range, so no slot-batch can fail to
  decode.
- **Sigmoid on the client.** Returning the logit instead of the probability
  saves about four levels and one approximation; the threshold moves to logit
  space.
- **OpenFHE's Chebyshev convention.** OpenFHE's `EvalChebyshevSeries` evaluates
  `c0/2 + Σ c_k T_k`, numpy's `Chebyshev` uses `c0`, so `export_model_txt.py`
  doubles c0. Left uncorrected, every logit is off by `Σ W2_k · c0_k / 2`, about
  0.468 in magnitude; an error whose mean equals its maximum is the
  sign of this kind of mismatch.
