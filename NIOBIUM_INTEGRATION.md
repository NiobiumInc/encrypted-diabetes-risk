# The compute stage on the Fog

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna)._

How the server's compute stage runs on a Niobium backend through the
[niobium-client](https://github.com/NiobiumInc/niobium-client) SDK, and what
the backend receives.

## Record, then replay

`src/diabetes_compute_sdk.cpp` runs the circuit that
`harness/cleartext_impl.py` reproduces in the clear, bracketed by the SDK's
`niobium::compiler()` calls:

1. **Tag the boundary.** The crypto context, the 21 feature ciphertexts and
   the relinearization key.
2. **Record, on a cache miss.** The circuit runs once with recording on and the
   FHE math skipped ("hollow" mode). That captures the instruction trace
   without computing a result.
3. **Replay, always.** `replay()` runs the trace on the backend named by
   `--target`, and `result()` rebuilds the logit ciphertext from what came
   back. The backend is therefore the only source of the answer.

The trace does not depend on which records are in a slot-batch, so each run
records it once, on slot-batch 0, and replays it once per slot-batch. The
harness runs the stage once per slot-batch (`--batch B`). Each invocation tags
the ciphertexts it loaded, without a file path, and its replay reads those.
`scripts/check_batches.py` checks this directly: it fails the run if a
slot-batch's scores match slot-batch 0's records rather than its own.

The harness records the trace afresh on every run, so a trace never outlives
the keys it was recorded with. The cache key is the circuit's shape (21 features, 16 units,
degree 27), the tier, the target and the opt level, and the trace is written
under the configuration's own work directory.

## Targets

| `--target` | Where `replay()` runs |
|---|---|
| `local` | `fhetch_sim`, the simulator built with niobium-client |
| `FOG` | a Niobium FPGA, as a Fog job |

`FOG` is a stable alias that the Fog resolves to its current device, so
clients do not have to track which one that is.

For `FOG`, the harness wraps each compute stage in
`niobium-client/scripts/fog submit`, which provisions a job, points the SDK at
it, and runs the stage. Keygen, encryption and decryption stay outside the job.
To use a replay server of your own instead, set `NBCC_FHETCH_SERVER` and the
harness forwards `--target` to it unchanged.

The harness passes `--opt-level O3` by default. Spell it that way when you run
the stage yourself: `--opt-level` is the form the SDK forwards to the backend.

## What the backend receives

For each slot-batch, one upload of about 340 MB:

| Part | Size |
|---|---|
| 21 feature ciphertexts | ~265 MB |
| relinearization key | ~50 MB |
| the recorded trace | ~20 MB |

What comes back is one logit ciphertext, about 5.2 MB. The circuit uses no
rotations and no bootstrapping, so there are no rotation keys or bootstrap
tables to send.

The secret key never leaves the client. Only `keygen`, `encrypt` and `decrypt`
read it, and the compute stage refuses to start if `key_secret.bin` is in its
directory. The patients' features and their risk scores are encrypted
throughout, so they stay confidential from the backend.

The model is different. Its weights, biases and Chebyshev coefficients enter
the circuit as plaintext constants, and they travel in the trace in the clear.
Running on a remote backend therefore discloses the model to whoever operates
that backend. This matches the threat model in
[`docs/DESIGN.md`](docs/DESIGN.md#5-security), which protects the patient's
data and treats the model as a plaintext operand rather than a protected asset.

## Building

`scripts/build_task.sh` builds niobium-client (its OpenFHE, `libnbfhetch`,
`fhetch_sim` and the transport client), then every stage against that OpenFHE.
If you build another way, link `libnbfhetch` into every stage, including the
client stages. The client's OpenFHE is instrumented, and its libraries
reference hooks that live there.

The root `CMakeLists.txt` does this for every target.
